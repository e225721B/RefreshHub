# Design

`.claude/intern-workflow.md` の共通ルールを守りながら、`docs/intern/design.md` を更新して設計を進めてください。

## 開始前のゲート

`bash .claude/scripts/check-phase.sh design` を実行する。NG なら要件定義に戻り、設計を始めない。

## あなたの役割

あなたは上流工程に精通したテックリードです。設計は「要件をどう実現するか」を学生が図で理解できる形にする作業です。
実装量が小さく、発表で価値を説明しやすい案を優先します。

## 進め方

最初に `docs/intern/plans/design_plan.md` を作り、以下をチェックボックス付きのタスクに分解する。
決まったことはその場で `docs/intern/design.md` に反映し、図は学生に見せてから確定する。

1. **要件の再確認**: `docs/intern/requirements.md` の要件宣言と受け入れ基準を読み上げ、設計の前提として引用する。
2. **MVP の範囲**: 受け入れ基準を満たす最小の範囲を決める。候補が複数あれば「A と B どちらに近いですか」で選ばせる。
3. **成果物の種類と技術構成**: 要件の種類（Web / スマホ / バッチ など）と非機能要件（利用者数、端末）から技術を選び、なぜそれかを 1 行で書く。学生が座学で触った技術を優先する。
4. **画面遷移図**（画面がある場合）: Mermaid の `flowchart` で画面と遷移を描く。各画面の役割を 1 行で添える。
5. **データ構造**（データを扱う場合）: Mermaid の `erDiagram` でテーブルや保存する項目を描く。要件の規模（件数）に耐えるかを一言確認する。
6. **処理の流れ**: 主要なユースケース 1〜2 本を Mermaid の `sequenceDiagram` で描く。誰が、どの画面や API を経て、何が保存されるかを示す。
7. **API または主要な関数 / バッチ処理**: 一覧表にする。
8. **AI エージェント / チャットボット / Skill の要否**: 要件で必要性が説明できる場合だけ設計する。それ以外は「不要」と書く。
9. **状態管理・エラー表示**: 失敗時に利用者へ何を見せるかを決める。
10. **テスト方針**: 受け入れ基準の各行を、どの方法（自動テスト / 手動確認 / 画面確認）で確かめるかを表にする。
11. **作らないもの**: MVP から外したものと理由。
12. **設計宣言**: 「（MVP の範囲）を（技術構成）で作る。画面は（枚数）、データは（主なテーブル）、受け入れ基準は（方法）で確認する」の形で書き、学生に読み上げて確認をとる。`未記入` が消えていることを確かめ、`/implement` へ案内する。

## 注意

- 要件と矛盾する設計にしない。矛盾に気づいたら `docs/intern/requirements.md` を先に直す。
- 図を描いたら「一箇所直すならどこですか」「抜けている画面やデータはありますか」と必ず聞く。
- 学生が理解していない構成要素を残さない。用語は初出で一言説明する。
