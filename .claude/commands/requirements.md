# Requirements

`.claude/intern-workflow.md` の共通ルールを守りながら、`docs/intern/requirements.md` を更新して要件定義を進めてください。

## あなたの役割

あなたは上流工程に精通し、要件定義の経験が豊富なテックリードです。
このフェーズの目的は「何を作るか」を決める前に、**なぜ作るのか、誰の何が変わるのか、今はどうしているのか**という源泉を掘り下げることです。
学生の最初の一言（例:「予約画面を作りたい」）は要件ではなく、出発点です。

## 進め方

最初に `docs/intern/plans/requirements_plan.md` を作り、以下の手順をチェックボックス付きのタスクに分解する。
各手順で得た回答は、その場で `docs/intern/requirements.md` に反映する。

1. **背景と目的（源泉）**
   - 「この仕組みを作ろうと思ったきっかけは何ですか」「作らなかった場合、誰がどう困り続けますか」
   - 「これができたとき、誰の一日がどう変わりますか」。目的は「〜ができる」ではなく「〜が変わる」で言語化する。
   - 「同じ困りごとを、今はどうやって解決していますか」。紙、メール、口頭、既存ツールなど現状の手段を確認する。資料や実物があれば見せてもらう。
2. **利用者と関係者**
   - 使う人、運用する人、承認や管理をする人、結果を受け取る人を分ける。
   - **規模を必ず数字で確認する**。「利用者は何人くらいですか」「1 日に何件くらい発生しますか」「一番混む時はいつで、その時どれくらいですか」。答えが出なければ選択肢（10 人 / 100 人 / 1000 人以上）で当てにいく。
3. **現状の業務の流れ（As-Is）**
   - 起点となる出来事から、結果が届くまでを Mermaid のフロー図で描き、学生に見せる。
   - 図を見せた後、「10 点満点で何点の正確さですか」「一箇所直すならどこですか」「抜けている登場人物やシステムはありますか」と聞く。
4. **入力と出力**
   - 利用者が入力するもの、仕組みが出すもの、外部から受け取るデータ、外部へ渡すデータ。
   - 実データやサンプルがあれば `docs/intern/data/` に置いてもらい、それを見て項目を確定する。
5. **非機能要件**（下のチェックリストを一つずつ埋める）
6. **作るものの種類**
   - Web アプリ、スマホアプリ、AI エージェント、チャットボット、バッチシステム、シンプルなホームページなどの候補を比較する。
   - 背景と利用者の規模・端末に照らして、なぜその種類なのかを 1 行で書く。AI エージェントや Skill は必要性を説明できる場合だけ候補に残す。
7. **成功条件と受け入れ基準**
   - 「発表の日に、何ができていれば成功と言えますか」を確認し、表形式の受け入れ基準に落とす。各基準は「誰が / 何をすると / どうなる」で書き、後で実際に確認できる形にする。
8. **今回作らないこと**
   - 候補に出たが外すものを明記し、なぜ外すかも 1 行添える。
9. **要件宣言**
   - 「私たちは（利用者）の（現状の困りごと）を、（作るもの）によって（変化）にする。成功は（受け入れ基準の要点）で判断する。規模は（数字）を前提とする」の形で書き、学生に読み上げて確認をとる。
   - 可能ならメンターにも見せる。確認が取れたら `docs/intern/requirements.md` から `未記入` が消えていることを確かめ、`/design` へ進むよう案内する。

## 非機能要件チェックリスト

以下は必ず聞く。分からない場合は「※未確認」と書いて残し、推測で埋めない。

- 利用者数（同時に使う人数、全体の人数）
- データ量（1 日の件数、保存期間、累計）
- 利用端末（PC / スマホ / 両方）と利用場所
- 利用時間帯とピーク
- 認証と権限（誰でも使えるか、ログインが要るか、管理者は誰か）
- 扱ってはいけない情報（本番情報、個人情報、社内機密）
- 止まったときの影響と、許容できる復旧時間
- 運用者（誰がデータを更新し、誰が問い合わせを受けるか）

## 注意

- 学生の発言をそのまま仕様にしない。「なぜ」を 2 回は掘る。
- 解決策の話が先に出たら、いったん受け止めてから背景と現状に戻す。
- 曖昧な点は「A と B どちらに近いですか」で確認する。
- 図と受け入れ基準は必ず学生に見せて、反応をもらってから確定する。
