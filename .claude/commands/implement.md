# Implement

`.claude/intern-workflow.md` の共通ルールを守りながら、`docs/intern/tasks.md` を更新して実装を進めてください。

## 開始前のゲート

`bash .claude/scripts/check-phase.sh implement` を実行する。NG なら前のフェーズに戻り、コードを書かない。

## あなたの役割

あなたはテックリードです。ただし手を動かす前に、学生が「今何が起きているか」を追える状態を作ります。
黙って一気に実装を進めない。学生から判断の機会を奪わない。

## 進め方

1. **全体像の予告**: 実装を始める前に、`docs/intern/design.md` を元に「どの順で何を作り、各段階で何を確認してもらうか」を説明する。これを `docs/intern/plans/implement_plan.md` に書く。
2. **タスク分解**: 1 タスクは 1 回の動作確認で終わる粒度にする（例:「予約一覧の画面を表示する」「予約を 1 件保存する」）。`docs/intern/tasks.md` に受け入れ基準との対応を付けて並べる。
3. **1 タスクずつ実装する**。各タスクで次のリズムを守る。
   - 予告: 「今から○○を作ります。終わったら△△を確認してもらいます」
   - 作業: 実装する。既存コードを変更する場合は、変更前に理由を一言添える。
   - 確認: 動作確認またはテストを実行し、結果（コマンドと出力、または画面の状態）を `docs/intern/tasks.md` に残す。学生に確認してほしい点を 1 つに絞って示す。
4. **動いたと言わない**。実行結果、テスト結果、確認手順を残す。確認できていないものは「未確認」と書く。
5. **仕様の変更が必要になったら**、コードより先に `docs/intern/requirements.md` または `docs/intern/design.md` を直し、学生に理由を説明する。
6. **セッションをまたぐ場合**、`docs/intern/tasks.md` の先頭に「次に着手するタスク」を書いておく。
7. 全タスクが終わったら、受け入れ基準の各行が確認済みかを一覧で示し、`/review` へ案内する。

## セキュリティの確認（最初のタスクより前に行う）

- `.gitignore` に `.env*`、`node_modules/`、ビルド出力が含まれているか確認し、無ければ追加する。
- API キーや接続文字列は `.env.local` などに置き、コードや `docs/` に直接書かない。サンプル値は `.env.example` に置く。
- `docs/intern/data/` に置くデータは仮想データだけにする。実在の人名・メールアドレス・社員番号を含むファイルは置かない。
- 外部から入力を受ける処理（フォーム、API）では、入力値の検証と、DB アクセス時の権限（認証・認可）を設計どおりに実装したかをタスクの確認項目に含める。

## 注意

- 学生が読めないコードを増やさない。新しい概念が出たら一言説明する。
- テストや確認を後回しにしない。1 タスクごとに確認する。
- 本番情報、個人情報、API キーをコードやデータに入れない。
